- 2026-10-13: **Changed:** a browser's session is not the token (issue #88 item 3, decision 0017). Tokens are unchanged for scripts, pipelines and agents. The database gains the table `sessions` (schema version 2, with a copy of the database written beside it first); an archive exported before still imports, because an archive now names the version of what it holds and not the schema's. - 2026-10-13: **Changed:** failed sign-ins are limited (issue #88 item 1, decision 0017). A wrong token, sent as a bearer token on a route that needs a sign-in or typed into the sign-in form, is counted against the address it came from and against its first 8 characters. A route that needs no sign-in (`/healthz`, the API description, the documentation) looks at no token, and a sign-in body the form does not accept (longer than 512 characters, or not text) is refused without being counted. The fifth failure of either within 15 minutes blocks it for one second, and each failure after that doubles the block, up to 15 minutes. A blocked request is answered `429` with `Retry-After` and the new error code `limited`, and its token does not decide the answer: one that is not in the form the server generates is not looked up at all. A right token the server generated passes all the same, so a pipeline is not stopped by whoever shares its address; passing does not end the block, which runs out by the clock. The token the server made from the value of `MAINWORTHY_OWNER_TOKEN` is one a person chose and gets no such pass, whatever it looks like (a generated token later copied into the variable is still the server's and passes). A session cookie is never counted; a request that also presents a token is judged by the token. The CLI prints `limited: too many failed attempts; try again in 4 seconds` and exits 4; the sign-in form says "Too many attempts. Try again in 4 seconds." Two new variables say which peer is the proxy in front and where it writes the visitor's address: `MAINWORTHY_TRUSTED_PROXY` (addresses and ranges) and `MAINWORTHY_CLIENT_ADDRESS_HEADER`. Set both or neither; one without the other, or an entry that is not an address or a range, stops the start with a line that says which. Without them a request from a loopback or private address, which is every request behind a proxy with such an address, is not counted by address, and a start in server mode says so in one line on stderr; a proxy with a public address is counted as one address, so its visitors share one count until the proxy is named. Before, a wrong token cost one request and nothing limited the next. **What breaks:** a reply's error code can be `limited`, a seventh code (the API description lists it); a script that keeps sending a wrong or revoked token is answered `429` instead of `401` once it has failed five times; a start in server mode that sets neither variable prints one more line on stderr. The instance at `mainworthy.com` does not set the two variables yet: `docs/deploy.md`, "The limit on failed sign-ins", says which values are expected there and how to check them.
- 2026-10-13: **people sign in as themselves** (issue #30, first slice; decision 0017): the server and the command line. An admin who is a person invites somebody with `mainworthy invite new <name> [--can read,answer] [--project <key>] [--expires 3d]`, which prints a link once (`<public address>/invite#<code>`; only the SHA-256 of the code is stored). The person accepts it with a password of 12 to 256 characters, a passkey, or both, and from then on signs in with their name and password or with the passkey. For a person who exists the link is a recovery, which the owner makes for anybody and an admin who is a person makes for themselves: accepted, it replaces every password and passkey the person had and ends their sessions. **New routes:** `POST /api/login` also takes `{ name, password }`, `{ passkey }` and `{ invitation, ... }`; `POST /api/login/challenge`; `GET /api/login/methods`; `POST /api/account/password`. A name, a password, a passkey's answer or an invitation code that is looked at and refused is answered the same whatever was wrong, and the reason is in the server's log as a code. **New operations:** `session` (list and end your browser sessions; an admin who is a person, anyone's), `credential` (list, register a passkey, remove one; the last stays) and `invitation` (create, list, revoke), each a command too. `GET /api/session` also says which session the request came by (`session`) and what the person signs in with (`credentials`). **New variable:** `MAINWORTHY_PUBLIC_URL`, the address people open the instance at. A passkey belongs to its host name, so one made there does not work at another name of the same instance; unset, there are no passkeys and a link has no host; a value no browser makes a passkey at stops the start, and so does one with a path or a query. **Changed:** `POST /api/login` refuses a body that holds a token and anything beside it, where it took the token before. The database moves to schema 4, with a copy written first. An archive still imports and holds no password, passkey or invitation: after an import the owner invites each person again. Forgetting a person also revokes their passwords and passkeys, erasing each hash and key, and their open invitations. A token still signs a browser in, and the owner's last token is still not revoked. The pages (sign-in, the invitation, "Your sessions", "Your sign-in") come with the web UI's pull request; until then these are routes and commands.
